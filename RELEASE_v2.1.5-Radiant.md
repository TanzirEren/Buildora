# Buildora v2.1.5 — Radiant ✨

Annotation processors now run during on-device builds — in a separate process, with clear logs and errors.

## 🧩 Annotation processing
- Real **JSR 269** API (`javax.annotation.processing`, `javax.lang.model`, `javax.tools`) is built into the app and drives ECJ's annotation-processing engine (Java 8 level)
- New screen **⋮ → Annotation processors**: add a Maven coordinate or a local `.jar`, enable / disable, limit to build types, set `-A` options, timeout, execution switches, browse generated sources
- Processors are found through `META-INF/services/javax.annotation.processing.Processor` (or an explicit class list); `META-INF/gradle/incremental.annotation.processors` tells Buildora which are *isolating* / *aggregating*
- Generated sources live per build variant and are compiled with your code; generated resources (e.g. `META-INF/services`) are packaged into the APK/AAB

## 📦 Dependencies
- Processors and their transitive dependencies are downloaded from Google Maven, Maven Central and JitPack, cached, and converted for Android once (D8)
- Version conflicts: the highest version wins and is written to the log
- **Offline builds** (Settings): only the local cache is used, with an explanatory error when something is missing

## 🛡️ Isolation
- Processing runs in a separate Android process: a crash, hang or out-of-memory cannot take Buildora or other projects down
- Timeout (default 10 min) and Cancel kill the process; it is also stopped after every run

## ⚡ Incremental
- All processors isolating: only outputs of changed sources are regenerated
- Aggregating / unknown processors, removed sources, or an output without originating element: full re-run (the log says why)
- Changing processors, options or versions always re-runs everything

## 🔍 Diagnostics
- Build log: processors found, rounds, timings, every generated file and its origin, processor notes
- Errors show the exact processor and source line; errors inside generated code say "generated by X from Y"
- Crash: processor, round, sources being processed and a trimmed stack trace
- Missing processor dependency: names the missing class and where to fix it
- Timeout / process death: names the processor that was running

## 🔗 Gradle interop
- Paste `annotationProcessor '…'`, `annotationProcessor files('…')` and `annotationProcessorOptions { arguments = [...] }`; imported Gradle projects are read the same way
- `kapt`, `ksp` and `project(':x')` are listed as **not supported**, never faked

## 📲 Update
Install `Buildora.apk` over your existing version — projects and keys are kept. Projects without processors build exactly as before.

## ⚠️ Known limitations
- **Verified so far:** the real AutoValue 1.8.2 and AutoService 1.0.1 processors and custom processors (rounds, claiming, options, errors, crashes, timeouts, incremental) through the real build engine on a desktop JVM, plus converting the processor jars with D8. **Not verified on a phone yet:** the isolated process, loading dexed processors with DexClassLoader, and the new screen.
- **Room, Glide, Dagger, Hilt are experimental:** they use this generic mechanism but could not be tested here (their jars were not reachable). Room verifies SQL with a desktop SQLite library that may not load on Android. Hilt needs a Gradle plugin for its class transform: only the plugin-free setup (extend the generated `Hilt_*` classes yourself) can work.
- **No KSP, no kapt** (needs Kotlin compilation). **No Gradle plugins.**
- Processors that use javac internals (`com.sun.tools.javac`, e.g. Lombok) do not work; processors compiled with APIs newer than Android provides may fail when they call them
- Source level stays Java 8; ECJ's annotation engine differs slightly from javac's, so a processor tuned only for javac can behave differently
- Dexing big processor stacks (Guava, Kotlin metadata, …) takes time the first time (cached afterwards); a processor run needs RAM

## 🐞 Found a bug?
Tap **Copy all** in the build error dialog (the processor log is included) and open an issue with your Android version and device.
